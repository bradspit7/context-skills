# Orchestrate — parallel subagents under explicit contract

Delegate to fresh subagents with precisely constructed context, run independent work concurrently, verify everything that comes back. Replaces `superpowers:subagent-driven-development` and `superpowers:dispatching-parallel-agents`; where they conflict, this wins.

The contracts below are deliberately mechanical. Follow them as written — they encode failures already paid for (skimmed reads, rubber-stamped findings, parallel agents colliding on shared files). Do not relax them because the work "seems simple."

## When / when not

**Use:** 2+ tasks with no shared mutable state; read sets too large for one context; multi-file audits, sweeps, migrations; plan execution where tasks are independent; review passes split by dimension.
**Don't use:** tightly coupled or sequential tasks (→ `execute-plan`); exploratory debugging where you don't yet know what's broken (→ `superpowers:systematic-debugging`); work small enough that dispatch overhead exceeds the work.

**Independence test before dispatching:** would any two agents read state another agent mutates, or edit the same file? If yes, serialize those two or isolate via worktrees — never "probably fine."

**Check the catalog before authoring a fan-out script:** glob `~/.claude/catalog/Workflow-recipes/` (start at `_index.md`) for a proven runnable that matches the pattern, and adapt it rather than re-deriving its hardening. (A hand-authored sweep convergently re-derived a proven runnable's guards at full authoring cost — and still missed one of its stages.)

## The prompt contract (every dispatch, no exceptions)

Subagents inherit NOTHING from this conversation. Every prompt must carry:

1. **Scope** — the one problem domain, named files/areas, and explicitly what NOT to touch.
2. **Context** — everything needed to act cold: error text, task text from the plan (paste it — never "read the plan file"), relevant project-law excerpts (no-push, append-only files, ownership, PHI/scope rules).
3. **Verification duty** — the exact command(s) the agent must run before reporting, with expected outcome.
4. **Output format** — structured: what it found/changed, evidence (command output), files touched, and a status from: `DONE` / `DONE_WITH_CONCERNS` / `NEEDS_CONTEXT` / `BLOCKED`.
5. **Write destination** — any agent that may WRITE (capture, probe, mirror, screenshot, scratch) gets an **absolute output directory, named in the prompt**, plus "write nothing outside it; no output redirection to absolute paths." Fan-out agents inherit the **launching session's cwd**, not the target's — so a fleet launched from repo X to work on target Y writes its scratch into **X's working tree**, silently and unignored. Measured: a 106-agent fleet launched from one client's repo to audit another's websites wrote **66 capture artifacts** into the launching client's git tree; `git check-ignore` matched **none** of them, so one `git add -A` would have committed one client's data into another's permanent history. Three agents each noticed and each correctly declined to delete another agent's working set — **nobody escalated**, which is the second half of the lesson: *"I noticed but correctly declined to act" is an escalation trigger, not a resolution* — report it in your status. **Guard, not just prose:** snapshot `git status --porcelain -uall` in every repo you launch from *before* dispatching, diff it after the fan-out, and treat any unexpected path as a failed post-condition — it is otherwise completely silent from the orchestrator's chair. **Distinct second half — a write into the RIGHT repo can still be lost:** if that output directory is **gitignored** (a `sandbox/`, `scratch/`, `tmp/`), the fan-out's artifacts do not survive a machine switch, because ignoring a directory answers *repo cleanliness* and not *must this survive a handoff*. Measured: a 12-agent design fan-out wrote three verified option fragments plus a 155KB comparison page **the owner still had to choose from** into an ignored `sandbox/`, and a plain push would have transferred none of it. So when a fleet's deliverable is something the OWNER must still act on, place it somewhere tracked, or class it explicitly at handoff — `device-handoff` Step 4 now enumerates ignored-but-touched paths for exactly this.
6. **Model** — typed agents never inherit the session model: an omitted `model` resolves to the agent-type's default (measured: `Explore` → Haiku). Pass it explicitly wherever judgment quality is load-bearing — all reviewers/verifiers, and readers when extraction is subtle.

## Recipe 1 — Read/scout fan-out (read-only, Explore-type agents)

For large read sets (context layers, audits, research):
- Slice the read set; one agent per slice; dispatch in a single message so they run concurrently.
- Contract: read every assigned file FULLY, chunking past every truncation — never sparse-search; return a structured extract (current-state claims with dates, locked decisions, open items, contradictions vs the summary you supply).
- **Verification quotes:** for every file over ~100 lines, the extract includes one short verbatim quote from its top, middle, and bottom third, with line numbers. A missing bottom-third quote for a file over that threshold means the file wasn't fully read — re-dispatch that slice. A **diagnostic/probe agent** (one that runs commands rather than reading a file) carries the same duty — it quotes the raw command output verbatim; measured 2026-07-09, the one fan-out agent with no quote contract was the one that returned placeholder garbage.

## Recipe 2 — Implementer per task, two-stage review

For plan execution with independent tasks:
- One fresh implementer per task, given the full task text + scene-setting context. Same-model default; drop to a cheaper model only for mechanical 1-2-file tasks with complete specs; keep the most capable model for review and integration judgment.
- **Never run two implementers concurrently whose file sets overlap.** Disjoint sets may run in parallel; overlap = serialize or worktree-isolate.
- After each implementer: **spec-compliance review first** (does the diff match the task — nothing missing, nothing extra), **then code-quality review**. Fresh reviewer agents; findings go back to the implementer to fix; re-review after fixes. Never start quality review before spec review passes; never advance a task with open findings.
- Status handling: `NEEDS_CONTEXT` → supply it, re-dispatch. `BLOCKED` → change something (context, model, task size) or escalate; never re-dispatch unchanged. `DONE_WITH_CONCERNS` → read the concerns before proceeding.
- **Reviewer dispatch contract** (ported from upstream subagent-driven-development v6 — eval-backed as a set on their benchmarks with documented run-to-run variance, so treat the gains as directional):
  - **A reviewer has a third verdict — `CANNOT_VERIFY_FROM_DIFF: <what the controller must check>`** — for a claim it cannot honestly adjudicate from the diff alone (runtime behavior, an external contract, an environment fact). The controller performs or dispatches that check itself; it never rounds this verdict into pass or fail. (`DONE_WITH_CONCERNS` is the *implementer's* channel, and crashed-agent handling covers dead reviewers — neither covers an honest live reviewer flagging an out-of-scope claim.)
  - **Named-risk scope budget:** reviewers work diff-first, and broaden outside the diff only for a concrete NAMED risk — stating the risk and what was checked. The per-task form of the review-tier doctrine: unbounded "review everything nearby" is cost, not rigor.
  - **Record each task's BASE commit when the task starts and review `BASE..HEAD` — never `HEAD~1`,** which silently reviews only the last commit of a multi-commit task and reads as a full review.
  - **Anti-coaching tripwire:** the controller never pre-rates severity or pre-filters findings in a reviewer dispatch — no "do not flag X", no "at most Minor", no "the plan chose this so don't question it". Upstream caught controllers doing exactly this in live runs, and the coached-away flaw shipped. (Distinct from Recipe 3's ground-truth rule: that bans handing a lens the author's *inventory*; this bans handing a reviewer the author's *verdict*.)
- **An agent's extracted string is advisory, not byte-authoritative, when it will KEY a write.** When a fan-out returns exact strings that a later `Edit` consumes as `old_string` (extract-then-apply sweeps, schema-sync, mass find/replace), re-read the real file bytes for the `old_string` rather than trusting the transcription, and let a deterministic re-check (byte-parity / regenerated diff) backstop the write — an LLM paraphrase silently swaps or drops a word, which fail-matches (safe) or, on a near-match, mis-edits the wrong span.

## Recipe 3 — Review fleet + adversarial verify

For audits/reviews: one agent per dimension (correctness, security, conventions, staleness…), dispatched concurrently. Before acting on findings that would drive real changes, run an **adversarial pass**: a skeptic agent per finding, prompted to REFUTE it against the actual code. Findings that survive get acted on; "plausible but wrong" dies here instead of in your diff. Adjudicating a pasted NUMBERED review: first prove the parse covers its own numbering ({1..N} exactly once — a bare count passes on drop+duplicate, observed live); an unproven parse is a logged coverage hole, never a silent drop.

**Verifier scope on a diff: "pre-existing" alone never refutes.** A skeptic asking only "did this diff *introduce* the defect?" is a false-negative generator for the *pre-existing root cause, newly exposed* class — the verifier's premise can be factually correct ("the old code did this too") while its conclusion is operationally wrong, because severity is a function of the diff even when the mechanism is not. Phrase the angle as: *is this defect introduced, **or does this diff increase its exposure, frequency, or severity**? Only a defect BOTH pre-existing AND not worsened by this diff is out of scope.* (Measured: two warranted fixes killed 0/3 and 1/3 on correct-premise "pre-existing" refutations — one a silent wait stretched ~300ms→10s, one a hidden broken state made user-visible; both shipped in the same commit the panel had cleared.)

**Verifier RUNS the repro for a deterministic mechanical claim — it does not reason to a verdict.** When a finding or fix turns on a mechanical question (shell/grep/regex/glob semantics, escaping, quoting, parse behavior, exit codes, string/number edge cases), model reasoning is a false-negative *and* false-positive generator — a plausible chain of reasoning about grep/regex/escaping is exactly what is wrong in these cases. The verifier runs a minimal repro (stdin/pipes, read-only — no fixture files, no redirection) and quotes the exact command + output; for a proposed FIX, it feeds the finding's own cited trigger through the fix and confirms it no longer fires (a fix that survives its own trigger is refuted). Reasoning is reserved for the judgment axes (severity, scope, YAGNI, fit). Measured: a 6-Opus-agent fleet (~427K tokens) confirmed a finding and proposed a grep fix that a 5-second 9-fixture repro proved still false-passes (the verifier reasoned about the grep instead of running it). The review-fleet runnable wires this as `MECHANICAL_REPRO_RULE` on every verifier prompt.

**A verdict is valid only if the lens actually OPENED the sources it cites — an ungrounded LIVE lens is a gap the dead-lens gate misses.** A live (not crashed) verifier that refutes — or confirms — a finding via an absence/novelty/reachability claim ("X isn't called anywhere", "it's already handled elsewhere", "documented in neither A nor B", "that landed") WITHOUT opening the cited source is asserting from reasoning, not evidence — and the dead-lens gate does NOT catch it (the lens *reported*; it just didn't *ground*). Measured 3× in one session, once inside the very verifier built to enforce this. Require each verifier to ENUMERATE `sources_opened` and treat any absence/novelty claim (in either direction) as INVALID unless the denied source is listed — grep the behavioral CONCEPT in the real source, don't reason to the verdict. The review-fleet wires this as `GROUNDING_RULE` on the generate verifier (with `sources_opened` on `VERDICT_SCHEMA`) and inside `SOURCE_AUTH_RULE` on the receive verifiers; the coverage LENS carries the same clause (an absence FINDING needs the denied source in `examined`). This is the *self-grounding* sibling of the ground-truth rule (a coverage lens enumerates the corpus it is handed; this governs the lens's own cited-source claims) and of the mechanical-repro rule above (both: ground the verdict in the artifact, never reason to it). It governs any verify fleet, including an ingest-verify pass adjudicating a kernel.

**Size the fleet before you spawn it — and name the tier in the dispatch line.** **First, before picking a tier at all, apply the HEDGE TEST: does the target ship its own fresh tests + mutation checks + a seeded positive? If yes it is HEDGED *even on a contract surface* — run the light tier AS the `tests / coverage` lens (*"are the new tests non-vacuous — would each fail on a broken engine; enumerate what they do NOT cover"*) and escalate to the full fleet only if that lens confirms a hole. Only an UNHEDGED target is sized by surface.** The hedge test is not a tier — it decides which tier you *enter*, which is why it runs first: a ladder read surface-first is matched and acted on before the carve-out is ever reached. (Measured: a 6-lens × 3-vote fleet over a self-tested 3340-line write-path diff ran **133 agents / ~3 hours** and was killed before synthesis with **zero acted-on findings**; the dispatcher reasoned "unaudited write path ⇒ full fleet" and never got to the carve-out.) Then, for an unhedged target: the full fleet (many lenses × 3-vote verify) is the *escalation*, not the default: reserve it for contract/safety surfaces (money, keys/secrets, auth, DB/state files, declared contracts) and genuinely-unaudited write-path work. Everything else — hedged, already-reviewed, prose/doc/process diffs — takes the **light tier**: a single skeptical pass, or 1-2 lenses with 1-2 votes through the same machinery (lens and vote counts are parameters, not a separate tool). State the chosen tier and its trigger in one line when dispatching; a full fleet whose stated trigger doesn't match the axis is cost, not thoroughness. (Measured on one heavy multi-project day: fleets — over a dozen runs — were ≈half of total usage at ~1.3-5M tokens per run, and fleets on hedged targets returned 1-3 fixes each.)

**Spawn every reviewing lens read-only** — reviewers, verifiers, critics, synthesizers, and any parse/transform helper that feeds them (every fleet agent that is not the orchestrator). A reviewing agent needs no write tools — give it a read-only `agentType` (`Explore`, or a tools-restricted reviewer) so a lens cannot edit the artifact it is judging. Prompt-level "review only" is NOT a guard when the agent still holds `Write`/`Edit`: default the tools off, and let the **orchestrator** (not the lens) apply fixes, deliberately, after reading the findings. This is paid-for — a completeness-critic running on the default write-capable agent once autonomously edited a live production file mid-gate when the pass was meant to be advisory-only. A read-only type like `Explore` still retains `Bash`, so seal the gate at the prompt level too: tell each lens in its prompt to use read-only inspection only (no mutating shell commands).

**Validate the fleet itself before trusting its verdicts.** A zero-finding run is ambiguous — clean code, a too-lenient gate, and a fleet that never read its target all look identical. Seed a *known* bug into a throwaway copy and confirm the fleet flags it — and make the seed exercise the verify-gate edge paths (a 1-1 tie, a crashed verifier), not just an obvious bug every verifier agrees on. An obvious-bug-only seed leaves the threshold logic unexercised and passes even when the gate is wrong (real case: a gate that confirmed 1-1 ties passed its obvious-bug seed because the verifiers happened to agree). A green review run is necessary, not sufficient — green-tests-not-sufficient, applied to the reviewer.

**The completeness critic is NOT only for zeros — and a 0-confirmed or 0-primary run is certainly not a clean bill of health.** The "gate the zero" framing fires the critic exactly when there is nothing to explain: its raw material is the *refuted* set, and a **non-zero run has more of it, not less**. So run it also when the panel **refuted a high/critical finding** (a panel that killed a HIGH owes an explanation) and whenever the target is a **stateful write path** — measured twice on runs where the zero-trigger was false: 6 confirmed incl. 2 HIGH → the critic resurrected a HIGH the panel had killed and named a missing modality (the single most valuable agent in a 51-agent review); 11 confirmed → byte-accurate adjudicators still missed a defect no finding touched, and one killed finding was dismissed on a reachability argument its *own verifier* had refuted. Compute this as a `criticRequired` flag with a `criticReasons[]` naming which trigger fired. **On top of that:** Refute-by-default verifiers systematically under-report bugs whose harm is conditional on a rare-but-real user path: a majority-refute is evidence about the panel's *reachability model*, not about the bug. On any run that confirms zero findings — or confirms only secondary/low-severity notes with **zero primary defects**, a de-facto zero for the real question — whether fleet-scale or a cheap low-lens pass, run a completeness critic before accepting the zero — an agent asked *"what's missing: which killed claims could the panel's verification method not actually reach? for each finding KILLED by a cited compensating control (a cache header, a guard, a fallback, an 'already handled elsewhere'), did that control actually reach the specific harm path, or is it adjacent-but-blind? what did no lens examine? did the dispatch prompt itself carry a false inventory?"* The critic is a finding mechanism, not garnish; skipping it as redundant on a clean run is backwards — a clean run is exactly when it is load-bearing. (Measured: a 52-agent fleet returned 15 candidates / 0 confirmed; the critic then recovered a real form-bricking bug the panel had refuted 3/3 on a true-but-irrelevant premise — and separately caught the dispatch prompt's own false inventory, the ground-truth rule below firing from the critic side. Separately, a secondary-only run — ≥1 confirmed, 0 primary — silently skipped the critic until the trigger was widened from 0-confirmed to 0-primary.) **And GATE the critic's OWN liveness:** a completeness critic run through a raw `agent()` that crashes, returns null, or degrades to a vacuous `{examined:"test",findings:[]}` reads as "no gaps" and lets the run report clean — wrap it exactly like any lens (an `isDegenerateLens` floor + one re-dispatch, then a coverage hole → INCOMPLETE); a crashed or vacuous critic is the ABSENCE of the check, never its clean pass.

**Coverage lenses enumerate ground truth — never hand a fleet the author's own inventory.** A fleet inherits the framing you give it: hand a coverage/correctness lens the instances *you already know about* and ask it to find holes, and it confirms your assumptions rather than auditing the corpus — it reproduces your blind spot. A lens that certifies *coverage* MUST derive ground truth itself (enumerate every real instance in the corpus; do not accept the handed list), or "adversarially verified" means "verified the author's framing." This is the fleet-blindness sibling of the seed-a-known-bug check above, and a corollary of green-tests-not-sufficient: a passing selftest plus one non-vacuous example is not corpus coverage. (Observed live on a write-path lint: a first fleet handed the two markup shapes its author already knew reproduced the blind spot and missed a silent-parse hole affecting most of the corpus; a re-run mandated to enumerate every real instance independently caught it.)

**Budget a synthesis/critic agent's payload PER-INPUT — a wholesale slice over a concatenated payload silently starves every input after the first.** `JSON.stringify({a, b, c}).slice(0, N)` is not a size guard, it is a **coverage lottery**: the truncation point is decided by whichever input happens to serialize first, so what survives is an artifact of key order rather than of importance, and it degrades **asymmetrically** — input 1 intact, input 6 absent — instead of degrading everything a little. **The starved agent has no signal, because a missing input and a nonexistent input are byte-identical to it.** Measured: a critic was passed `JSON.stringify({maps, adjudications}).slice(0, 14000)`; the FIRST map's `notes` field alone consumed the budget, so the critic received **one of three maps, its notes cut mid-token, and ZERO of the two adjudicator results** — while its prompt told it there were three maps and two adjudicators. It reported this as the run's biggest gap only because it independently opened 15 files; a less thorough critic would have synthesized confidently over 1/6 of the evidence and reported nothing wrong. **Three fixes, cheapest first:** (a) **pass a COUNT the agent can check** (*“you were sent 3 maps and 2 adjudications”*) so a starved payload becomes *detectable* rather than invisible — the fail-observable half, and the sibling of the dead-lens gate (that catches a lens that did not REPORT; this catches a synthesizer that was not TOLD); (b) **budget per-input** — `N/inputCount` chars each, so every input is represented; (c) **summarize each input to a fixed budget before concatenating**, rather than truncating the join. Prefer a **per-item cap enforced at the schema layer** (with explicit self-truncation instructions to the agent) over any slice of an assembled response. Sibling of the ground-truth rule directly above — a lens inherits the framing you hand it; here it inherits a **denominator you silently cut**.

**Enumerate by FILE and by MEDIUM — and declare what the lens cannot perceive.** The rule above fixes *whose list* a lens trusts; this fixes *what it can perceive at all*, and the gap is invisible in the output because a text-only lens reports cleanly on a corpus whose worst item is a photograph. Make each coverage lens state **how many files exist vs how many it opened**, and **report any medium it could not open as UNEXAMINED**. Read-only lenses (a git/cat/grep/ls seal) *cannot* open images, audio, video or binaries — so for them this is a **declare-only** duty; opening those media needs a differently-equipped agent the orchestrator dispatches deliberately. And any page-class or file-class **carve-out in a lens prompt is itself a coverage hole that must be NAMED in the output**, never a silent filter. (Measured: a 5-lens / 69-agent sweep of a 19-file site — 12 confirmed, 0 fabricated quotes, every lens working as designed — had covered **5 of 19 files, prose only**; the two worst items were an `<img>` alt asserting a named individual's identity onto stock imagery, and a carve-out written for article body copy that excluded a whole directory holding the worst textual claim.)

**A comparative fleet is structurally blind to whatever both artifacts SHARE.** An A-versus-B framing can only validate or kill claims *about differences* — a shared total absence produces no difference, so no lens ever raises it, and the report still looks comprehensive. So **any comparative review must include at least one lens measuring ONE artifact against an EXTERNAL standard** (a requirements checklist, a spec, a regulatory baseline, a category norm), never against the other artifact — a required dimension, not an optional extra. And treat an unusually **low refutation rate** in a comparative fleet as a **framing signal to investigate**, not a quality signal to report. Applies to any two-candidate evaluation: A vs B, old vs new implementation, vendor bake-offs, before/after migration audits, competing designs. (Measured: 7 lenses × 2 sites, 153 findings, 79 confirmed — and no lens reported that *both* properties had zero analytics of any kind, making all 79 findings unmeasurable before and after, nor that *both* lacked required legal notices; one completeness critic found both.)

**Rewrite-verify needs a currency lens, not just a drop/coverage lens.** When the fleet verifies a *rewrite or compression* of a source-of-truth doc (a HANDOFF/CONTEXT rotation, a status/state file), a drop/coverage check proves "nothing lost" — not "everything kept is still true." Add a lens that RE-DERIVES each carried current-state claim (tracked/untracked, committed/uncommitted, ahead-count, config value) from live state (`git ls-files`/`status`/`log`, the config file) — a faithfully-preserved claim can still be false. (Observed live: a 3-lens fleet certified a HANDOFF compression as dropping nothing while it carried two already-stale git-state lines an external review then caught.)

**Codification review needs rule-soundness + sibling-propagation lenses on top of fidelity.** When the fleet's TARGET is a RULE / DOC codification (a new or edited always-loaded rule, a skill instruction, a memory kernel) rather than code, the code lenses don't fit, and a *fidelity* lens is necessary but NOT sufficient: it certifies the kernel was TRANSCRIBED faithfully, not that it is SOUND or that the edit reached every sibling. ADD two: **(1) rule-soundness** — steelman the OPPOSITE of the claim: test the stated direction and its converse *separately*, requiring both to hold only when the rule claims equivalence/symmetry — otherwise use the converse to hunt over-reach (fires where it shouldn't), not as an automatic validity condition, since many sound rules are one-way implications. Check the prose summary agrees with the operational part (reference code / gate / worked example); name the strongest case the rule gets *wrong*, don't confirm faithful encoding. **(2) sibling-doc propagation** — independently enumerate EVERY doc that could carry the same claim (the always-loaded rules doc, memory, the roadmap/HANDOFF resolved rows, skill copies + their mirrors/public copies) and grep each for the *stable identifier, the old wording, AND the behavioral concept / likely paraphrases* — a literal old-phrase grep misses a paraphrased sibling — confirming the edit reached all of them in one pass. And when the codified rule makes a UNIVERSAL scope-claim ("governs any X", "every writer/gate", "any ingest-verify pass"), this lens ALSO enumerates every X-INSTANCE in that class — every runnable/gate, not just every doc — and confirms the rule was WIRED into each, or the claim NARROWED to what shipped; a "governs any verify fleet" beside a still-failing member is a doc-over-claims-code trap (caught live when a grounding-rule codification over-claimed while two sibling verifier lenses still failed it — by the completeness critic, after this very lens saw one instance and dismissed it "out of scope"). **This sweep-obligation binds a DESCRIPTIVE/completion universal (read as ALREADY wired into every member), NOT a normative standard (a bar-to-meet over an open-ended class — e.g. "green-tests-not-sufficient governs any write-path change" — which owes no sweep and must not be narrowed); the tell is whether a reader takes the claim as "already closed" (descriptive → sweep-or-narrow) vs "the standard to meet" (normative → exempt).** Keep the fidelity lens too — a sibling garbled into a *wrong* paraphrase is neither stale nor unsound, and only fidelity catches it; ADD these two, don't replace it. Compose with the ground-truth rule above and the completeness critic on a 0-confirmed or 0-primary run. (Observed live: four internal agents on a fidelity-heavy pass passed a rules codification; an external review then caught the rule was internally unsound — asymmetric, one-direction-only — which fidelity cannot catch, and a second lens caught the reframe reached the main doc but not its sibling rows.) Sibling of the doc-drift discipline + the ground-truth rule above. **When the fix REWRITES a conditional prompt or template clause (e.g. a verifier prompt that branches on target kind), prove the rewrite REMOVED the old framing rather than layering over it: render the assembled prompt in each branch and assert the removed phrasing is ABSENT in the fixed branch and PRESENT (byte-identical) in the unchanged branch — a captured-output diff, not "the fixed path works." Appending a corrective instruction after a still-present competing clause is the fix-by-adjacency trap; two contradictory authorities leave the model to pick.** **The same captured-prompt discipline also catches a CANNED-STUB test that proves only plumbing:** when a pipeline test stubs the downstream verdict, feed a DISTINCTIVE input token and assert it reaches the assembled prompt/payload the next stage consumes — a stub that supplies the very signal the code should PRODUCE reads GREEN even when the upstream stage never passed the input down, so the omission ships (a receive verifier told to grade the reviewer's fix never interpolated the fix into its prompt; a canned-verdict smoke test read clean; the fix was a captured-prompt assertion that a distinctive fix string appears in the assembled prompt).

**Write-path fleet — the hardened gate (use when the change decides what gets *written / filed / matched / registered*).** The generic pass above is not enough for write-path logic; this gate has already paid for real silent-data-loss bugs. A correct write-path fleet MUST hold all of:
- **Named dimensions** including a *reproduce-the-specific-mis-write* lens (not just generic correctness) and reachability of the new state, alongside the standard lenses.
- **Strict majority of the *expected* votes** (default 3 skeptics/finding); a missing or crashed vote counts as **refute**, never a silent confirm.
- **`needsReverify` bucket ⇒ `status: INCOMPLETE`** — a crashed/timed-out verifier surfaces for hand-adjudication, never silently folded into refuted; and a NONEMPTY bucket forces the run's top-level `status` to INCOMPLETE (never COMPLETE), reported alongside a `verificationCoverage {expected, completed, exhausted, indeterminate}` counts object — so a partial verify burst (many verify slots died on a usage limit) never reads as a clean full run. Extends the dead-lens fail-closed rule from lens-death to verify-slot-death.
- **Exactly-one source coverage** — every finding maps to exactly one input; a missing / duplicated / invented mapping forces the fallback (no silent drop, no double-count). For the receive-mode parse of a pasted numbered review, Recipe 3's parse-coverage proof applies.
- **One shared concurrency pool** below the runtime's ~14 cap (default ~6) + retry of crashed slots, so the verifier burst can't trip the rate-limit into false-refutes.
- **Read-only lenses** — every non-orchestrator agent in the fleet (reviewers, verifiers, critics, synthesizers, parse/transform helpers) runs under a read-only `agentType` (e.g. `Explore`) AND is told in-prompt to avoid mutating shell commands (`Explore` keeps `Bash`); a gate that can mutate the artifact under review is not a gate. The orchestrator applies confirmed fixes itself, after adjudication. Model pins per the prompt contract (item 5): every lens/verifier call passes its model explicitly (the fleet's role defaults or a per-lens pin).
- **Different-model verifiers (ratified 2026-07-01; canonical form assumes single-model access)** — when a second strong model is available (a different lineage such as Codex, or a second strong Claude tier), run verifiers on a **different model** than the reviewer/judge lenses, so no finding is confirmed by the model that raised it. With single-model access, a same-model fleet is the validated baseline — but the model that AUTHORED the change is never its *sole* certifier (angle-diverse refute-by-default verifiers + the orchestrator's human-adjudicated apply step carry the gate). Pin any security-adjacent lens AND its verifiers to a model without cyber-classifier refusal exposure (Opus 4.8 today — Fable 5 false-positive-refuses security-lens prompts even on defensive review, and a refused lens agent returns null, which otherwise masquerades as a clean zero-findings pass: surface it as a coverage hole, never a clean zero).

**Point the fleet at STAGED bytes, not working-tree drafts.** The fleet judges the bytes it reads — so complete all edits, `git add`, verify the index (`git show :path` / `git diff --cached`), and commit unchanged. A post-verdict edit RE-OPENS verification for that file: the reviewed bytes and the committed bytes must be identical, or the review certified something you didn't ship. (Companion to in-fleet source-authentication, which hardens the *verifier* to authenticate the reviewer's quoted strings against real source; this governs *which* bytes the caller reviews.)

**Receive mode — adjudicate the FINDING and its proposed FIX on separate axes, and match the frame to the TARGET.** When the fleet adjudicates an EXTERNAL review (receive mode), two receive-specific rules the generic gate misses: **(1) a valid finding is not a valid fix** — grade the reviewer's proposed *remedy* separately from whether the finding is real: does the fix reintroduce the exact failure the current code's conservatism deliberately guards against (e.g. "resurface on ANY error" where the narrow guard exists to prevent a flap)? A finding can be CONFIRMED (valid) while its fix is a regression — confirm the finding, flag the fix, and never apply the reviewer's fix verbatim on the strength of the finding's validity (a good runnable reports this as a per-verdict fix-direction grade plus a fix-concern flag on the confirmed finding). **(2) a review OF A PROPOSED DESIGN is not a review of committed code** — for a design/plan target the artifact is the DESIGN TEXT: verifiers judge whether the design's claim holds *when implemented as written*, NOT whether the current code already exhibits the defect ("the code doesn't do this yet" is the expected state of an unimplemented design, never a refutation). Tell the fleet the target is a design (a `reviewTarget:'design'`-style flag) — or, for a SMALL code-anchored design review, adjudicate by direct inspection: a measured fleet spent well over a million premium-model tokens to confirm a handful of findings a direct read already had, plus a couple of false refutations.

Run the project's validated review-fleet workflow when it provides one (generate mode for a diff; receive mode to adjudicate an external review's claims); reproduce every guarantee above from scratch only when it doesn't. A from-prose re-derivation that drops any of these is the exact failure this contract prevents. **Codification/doc reviews are NOT an exception** — the runnable covers them (pass the three codification lenses above as `args.dimensions`), so a hand-rolled bespoke codification script IS the from-prose re-derivation this warns against: measured 3× in one session, it silently drops the runnable's `isDegenerateLens` floor so a schema-failed rule-soundness lens's `{examined:"test",findings:[]}` fallback reads as a LIVE clean lens (COMPLETE / `deadLenses:[]`) and runs an ungated caller-critic — both dead-lens holes above, reintroduced by re-deriving the tool from prose.

## Recipe 4 — Long-running commands

Any command expected to run >2 minutes (sweeps, builds, full suites, recon): launch as a background task and keep orchestrating; collect on completion. Never sit idle behind a long command, and never poll in a sleep loop. When a project skill *wraps* such a command, write this discipline into that skill's own text ("background launch, never poll, keep working or end the turn") — the instruction living in the skill is what makes every future session do it unprompted.

**The completion notification reports the exit status of the LAST command in the launch, not of the command under test.** `cmd; echo "RC=$?"` notifies *`echo`'s* status — always 0 — and `cmd | tail -30` notifies *`tail`'s*, so a genuinely red suite arrives labelled *"completed (exit code 0)"*. Make the command under test the **last** thing in the launch, or capture and re-exit (`rc=${PIPESTATUS[0]}; …; exit "$rc"`). This is nastier than the ordinary pipe-swallows-the-status trap: that one corrupts a value you then go and read, while this corrupts the **out-of-band summary that arrives unprompted and gets read INSTEAD of the log** — an operator trusts it precisely because they did not have to go looking for it, and nothing about `exit code 0` hints it describes a different command than the one named beside it. Read the runner's own verdict line in the log before believing any completion summary. Measured twice in one day by two different agents, each of whom had already narrated the rule earlier in the same session.

## Recipe 5 — Big fan-outs via the Workflow tool (when the harness offers it)

Prefer a Workflow script over hand-rolled Agent batches once the fan-out has structure: ~10+ agents, multi-stage pipelines (mine → verify → synthesize), loops/conditionals, or wherever validated structured outputs matter. The prompt contract above carries over verbatim — every workflow agent prompt still needs scope, cold-start context, verification duty, and output format. Workflow-specific contracts (proven on a 25-agent corpus-mining run, 2026-06-10):

- **Schema-enforce every agent output** (the `schema` option) — validated JSON beats parsing prose, and mismatches retry at the tool layer instead of corrupting the pipeline.
- **The default `agent()` is NOT tool-free — never design "the verifier can't read files" into a workflow.** A workflow agent with no `agentType` keeps file tools (Read/Grep), and measured behavior (8/8 default-type verifiers in one A/B trial) is that it re-reads source even under an inline-only prompt — and a lone verifier can mislead *itself* on a failed search (one false-refuted a real finding when its own grep came back empty). Consequences: (1) a "premium never does file I/O" rationing claim is aspirational unless the agent type actually removes the tools — the enforceable lever is **self-contained evidence** (locator + verbatim excerpt) so the verifier has no reason to re-read; never assume it can't, never assume it can; (2) a prompt-level "do not read files" clause is steering, not containment — when blindness matters (blind trials, substrate isolation), pair it with an audit mechanism that *catches* a read (sentinel echo, deterministic leak scan).
- **Keep schemas FLAT — a schema-validation death loop THROWS.** An agent that repeatedly fails its schema hits the StructuredOutput retry cap and the `agent()` call throws (measured ~480K tokens burned across 3 crashed fleets). Few required fields, shallow nesting; a `notes: string` catch-all beats mirroring a deep structure. And contain the blast radius: `try/catch` any `agent()` whose death shouldn't kill the run (inside `pipeline()`/`parallel()` a throw becomes a `null` item — `.filter(Boolean)` and log it), so one incorrigible agent degrades to a logged hole, not a dead fleet.
- **Auto-retry crashed stage agents — the human is never the retry loop.** A single-agent stage (a lens, a parser, a synthesizer) that returns null (crash / 529 / refusal) or throws gets one **sequential** in-script retry before falling through to its coverage-hole/fallback path; never re-burst the concurrency that killed the first attempt. The review-fleet's `stageAgent()` is the reference implementation (its verify burst has its own retry rounds); measured failure mode without it: the user hand-types the re-run.
- **Schema-valid is NOT non-vacuous — deterministically vacuity-check structured returns.** A schema-conformant agent can still return placeholder text that passes both validation and `.filter(Boolean)` (measured 2026-07-09: an agent returned `{"answer":"test","evidence":["a","b"]}` past both). Gate the required content fields on min-length + a placeholder-pattern reject (`^(test|todo|tbd|n/?a|[a-z0-9])$`), and spot-grep one cited quote against its real file. A vacuous return takes the SAME one-sequential-re-dispatch-then-logged-coverage-hole path as a crash — never a silent accept. Reference recipe: `~/.claude/catalog/Workflow-recipes/extract-then-judge.md` (embeds the `isVacuous` gate).
- **A status/verdict field means the CLEAN RESULT, not "the stage ran" — and its NAME must not over-claim.** A return field like `verified` whose value is `!!ranVerify` (the verify stage produced a payload) READS to a downstream consumer as "is clean/confirmed" — but it also holds the items the verifier REFUTED, so a consumer keying on it silently treats a flagged item as real. Name the field for exactly what it checks: `adjudicated` (a binding verdict was produced — survived OR refuted) is a SUPERSET of `survivors` (`survives===true`), and only the latter is clean. In a verify→(fix) pipeline with NO re-verify stage, a fix-stage-patched item is "unconfirmed," never "verified." This is green-tests-not-sufficient applied to a status classifier and its serialized field NAMES — the suite stays green while the mis-named field ships and mis-signals every downstream. (Measured: `scout-then-verify` returned a `verified` array that included refuted findings; renamed to `adjudicated`, `survivors` the sole clean set. Sibling of the `needsReverify ⇒ status: INCOMPLETE` status-honesty rule in Recipe 3's write-path gate.)
- **Post-run output extraction: use the standing extractor, not hand-rolled probes.** `python ~/.claude/skills/orchestrate/scripts/task-output.py` — no args: newest run's summary + result shape; `--key primary.0.title` one node; `--logs`; `--agents` per-agent table; `--agent <id|label>` one agent's structured output; `--extract out.json` every agent's output (fleet-resume step 1). It already handles the `result` wrappers, entity-escaped JSON, and Windows cp1252 traps that hand-rolled probes re-fail on every time (measured in 4 independent sessions).
- **After every workflow run, the user gets a plain-English recap first.** Lead the next message with 1–3 sentences: what ran (N agents over what), what came out (counts plus one concrete example), what happens next. Never open with — or worse, only paste — the raw return value; the run isn't done until the human can tell what it did.
- **`Workflow({name})` does NOT resolve a project-local `.claude/workflows/` — use `{scriptPath}`.** Measured: a recipe ported to `<project>/.claude/workflows/section-options.js` returned `Workflow "section-options" not found. Available: deep-research, code-review`, while `Workflow({scriptPath: "<absolute path>"})` worked first try. This bites precisely because catalog recipes ship as project-local `.js` and the tool's own docs ("built-in or from `.claude/workflows/`") read as though by-name works. **Deliberately not over-claimed:** whether a *user-level* `~/.claude/workflows/` resolves by name was **not tested** — this covers only the project-local case actually measured. (Distinct from the CRLF trap on the same option: a `scriptPath` file with CR bytes is rejected by the permission layer as "control characters", which is a *different* failure from the name never resolving.)
- **`args` may arrive as a JSON string, not the object you passed** — parse defensively at the top: `let A = typeof args === 'string' ? JSON.parse(args) : (args || {})`. Skipping this does not error: a truthy string makes `args.foo` silently `undefined`, so every option falls back to its default — the symptom is a script that ignores its inputs (e.g. a review fleet that reviews the *default* target and reports nothing).
- **Join stage-N verdicts back to stage-N−1 findings mechanically** (normalize + fuzzy-match on the key field) and **count coverage per kind**. Verifiers skip findings silently — the reference run's first wave covered only ~53% of findings. Dispatch a top-up wave over the measured gap; never average over it.
- **Authenticate claims against sources in the verify stage:** the verifier greps the source material for a distinctive substring of each claim's quote; `quote_found=false` kills the finding regardless of plausibility (8/200 died this way in the reference run).
- Launch in the background and keep orchestrating (Recipe 4 discipline applies); collect on the completion notification.
- No Workflow tool on the current surface → run the same structure as sequenced Agent-tool batches. The contracts, not the tool, carry the quality.

## Integration (the orchestrator's own duties)

- **Continuous execution:** no "should I continue?" between tasks. Stop only for an unresolvable `BLOCKED`, genuine ambiguity, or completion.
- **When executing a written plan:** first run execute-plan's Step 1 yourself (full plan read, assumption/currency check, branch discipline), and as tasks complete, check off their `- [ ]` boxes in the plan file and log deviations there — orchestrated execution gets the same plan integrity as inline execution.
- Read every summary; spot-check claims against the actual diff/files — agents can be systematically wrong with full confidence.
- Check for cross-agent conflicts (same file edited twice, contradictory extracts) before accepting results.
- **Run the project's full verify loop yourself once at the end.** Per-agent verification doesn't cover integration.
- **No silent truncation:** failed, skipped, or dropped agents are reported with what they covered — a partial fan-out that reads as complete is worse than a smaller honest one.
- Wrap-up: commit per project law (never push unprompted); on a feature branch route to `superpowers:finishing-a-development-branch` — asking its integration question as a one-line prose question with a single recommendation, never the choice-button UI; suggest `/update-context` if the session is ending.

## Red flags

- Dispatching an agent that must "read the plan/handoff first" — paste the content; the file read costs more than the paste and the agent may read the wrong version.
- Accepting an extract missing its bottom-third quote (for a file over the ~100-line threshold), or a "DONE" with no verification output — contract violation, re-dispatch.
- Fixing an agent's half-done work by hand in the orchestrator context — dispatch a fix agent with specific instructions instead.
- Two implementers in flight on overlapping files "because they're quick."
- Relaxing review order (quality before spec) or skipping the re-review after fixes.
- Trusting a verifier's verdict label without reading its evidence fields — schema-enforced labels still drift semantically ("confirmed" can mean "the pattern is real" rather than "the claim survives"; a verifier whose *reason* refuted a claim was measured setting `refuted=false` — it answered "is the code fine?" instead of "does the claim survive?"). Pin the question mechanically where the tool allows it (per-field schema `description`s), AND classify from the cited evidence; mechanically join verdicts back to findings and count coverage — re-dispatch the gap, never average over it.
